## Persistent memory protocol

After reading this guide, always read `docs/memory/project.md`, then `PROGRESS.md`, `ARCHITECTURE-ESSENTIALS.md` and the read order in `CLAUDE.md`. These files restore context across sessions without needing earlier chat. This is a file-based protocol, not an automatic background memory service; an agent must actually read the files.

`PROGRESS.md` is the short operational resume point; project memory stores durable decisions, constraints and unresolved choices. Update both at the end of relevant sessions. Record dated facts and their evidence; distinguish plans, implemented code, verified checks and external setup. Never store secrets, private chain-of-thought or real payroll data.

If role-specific work is explicitly delegated, the orchestrator supplies scope, applicable rules and context and may create `docs/memory/<role>.md` for the designer/architect/etc.; each worker reads project memory and its assigned role memory. No agents or role files are created by this planning update. No role memory overrides architecture rules or user instructions.

The user can revoke a memory entry: mark it revoked with date and replacement before further work. A revoked entry grants no authority. Resolve contradictions against current user instructions and architecture; ask about unresolved conflicts. Ask the user about new-project intent and design before starting; this repository is an existing project. Write specifications, phase plan and testable acceptance checks before implementation, then follow the phase approval process.
