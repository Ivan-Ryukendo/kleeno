# Command reliability inventory

R6.1, source baseline integration `05603d8`, inspected 2026-10-11. This table records implemented controls and conservative retry guidance. It does not add a retry service, change API contracts, prove deployment acceptance or mark every command idempotent.

## Contract

A retry is the **same actor, tenant, object and unchanged command**, with the same client key where supported. A new UUID is a new command, not a retry. On conflict, reload current evidence and obtain a fresh human decision; never replace an expected revision silently. Correlation IDs link requests but are not idempotency keys. Guard checks remain required on every request, including a retry.

State compare-and-set (CAS) rejects transitions from a stale state; it is not equivalent to a command key or a field-level edit revision. A unique natural key prevents duplicate entities; it does not by itself guarantee an atomic response or exactly one audit event. A route returning a previous result does not imply the entire surrounding operation is transactional.

Payment attempts are saved before Circle calls. UNKNOWN requires independent Arc/Circle reconciliation; never create a new attempt/key to escape uncertainty. The [existing recovery implementation](../src/core/payments/agent.ts) distinguishes same-key continuation from a new attempt: with no saved Circle transaction ID, Arc `isPaid=false` and a fresh gate pass, it can submit with the same persisted key; with a saved Circle ID it follows that transaction. A proven Circle failure with nothing paid on Arc becomes PAYMENT_EXCEPTION, without an automatic second attempt. This describes current code, not a rule amendment or permission to operate payments. A retry never bypasses [the single gate](../src/core/payments/gate.ts), kill switch, SIMULATION boundary, plan hash, four-eyes or fresh re-auth requirements. No provider call, funds movement or remote database change was performed for this inventory.

## Every command-capable handler

Ordinary GET/HEAD read routes are omitted; OAuth callback and paid verification bookkeeping are noted separately below. Each source link points to the actual handler; repository links substantiate the control rather than treating a schema field as proof of database enforcement.

## GET callbacks and read-side bookkeeping

- GET [OAuth callback](../src/app/auth/callback/route.ts) consumes an authorization code, exchanges a session and may write auth audit/cookies. It has no client command key/revision. Do not replay a used OAuth code; restart sign-in after failure. Return paths remain allowlisted.
- GET [x402 Verify](../src/app/api/x402/verify/route.ts) is a read-only receipt answer with payment verification/rate-limit bookkeeping. It has no payroll command or payment authority; never treat a paid read as permission to mutate payroll or retry worker payments.
- GET exports/readers can consume rate limits or audit reads; their HTTP method alone does not promise zero bookkeeping. This inventory concerns business commands and mutation/preview/export handlers, not every read-side log row.

## Gaps to carry forward

- Config proposals, run/worker/company creation, compensation versions, invitations, comments and several profile/team commands lack a general client command key and/or edit revision. A natural uniqueness constraint or state guard is narrower than a full retry contract. Inspect the existing result after ambiguous responses before issuing a new command.
- R6.2 is the existing concurrency-test task for config, worker, adjustment, exception and review edits. This documentation does not close it. Keep the state/revision/key distinctions in those tests.
- Bulk commands can complete only part of their work before a failure; identify completed objects first. Do not assume a bulk HTTP request is one database transaction.
- Re-authentication is supplied afresh for the action request; never store passwords/TOTP or replay a user's credentials in a background job. Job/outbox justification belongs to R6.5, not this inventory.
- Payment and billing provider uncertainty must remain visible. Retry identity does not prove settlement, successful collection, atomic audit, or safe automatic failover.
