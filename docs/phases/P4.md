# P4 — Payments (Oct 4–7)

Status: **draft 2026-10-03, waiting for the user's approval.** Branch: `p4-payments` (from `main` after P3b merged, PR #10). Spec: ARCHITECTURE §12–§15, rules 16–28, PRD criteria 10–17, 23, 30, 34, 35.

## Goal
A LIVE_TESTNET run goes from payroll approval to settled USDC on Arc through the real, guarded path, driven from the UI by the right people: approve → obligations → plan → signature → `openRun` → gate → payment agent → Circle → `PayrollGuard.pay` → Arc receipt matched → SETTLED → RECONCILED. A company gets live payments through a request, platform approval, automatic wallets + guard, and an Owner switch (re-auth + TOTP). Gateway top-up and Kleeno Verify (x402) come last and are the first things cut.

## Build slices (each ends green before the next)
1. **Approval and obligations.** Payroll approval (binds `calculation_hash`, re-auth, S16); recipient-change confirmation by the other role (re-auth); obligations created from the approved calculation lines (idempotency key, on-chain key = keccak256 of the obligation UUID, recipient snapshot); deterministic signals (`AMOUNT_RATIO`, `RECIPIENT_CHANGED`, `FIRST_PAYMENT`, `CONFIG_VERSION_CHANGED`).
2. **Batches and authorization.** Batch lifecycle, fallback plan (one batch, all obligations, no holds; the AI Planner is P4b), manual holds, `plan_hash`, plan signing (re-auth, different user from the payroll approver, DB trigger), hold release into a new batch, then `openRun` from the DB-loaded obligation set. Full gate matrix (S08) with one test per failing check.
3. **Execution, recovery, settlement.** Payment agent runs the authorized batch obligation by obligation (inline in the signing request, then resumable); attempt row saved before the Circle call; Circle webhook (verified, deduped, hints only); recover route + dashboard-load recovery; settlement reconciliation from the Arc receipt (S30); `closeRun`; run states `PAYMENT_IN_PROGRESS → PARTIALLY_SETTLED | SETTLED → RECONCILED`; correlation ID end to end (S33).
4. **Live-payments activation.** `companies.live_status` (`NOT_REQUESTED → REQUESTED → APPROVED → PROVISIONED`, `REJECTED`); Owner requests; platform admin approves (MFA); provisioning creates approver + agent wallets and deploys the guard, each step stored and idempotent (`setup-wallets` and `deploy-guard` logic moves into `src/server/circle/provisioning.ts`); Owner switches ON (re-auth + TOTP, two members with the two roles); OFF for payment approver or Owner. Demo and sandbox blocked by DB CHECK. `scripts/live-payments.ts` keeps working and gains `--close-open-runs`.
5. **Standing authorization.** Create (payment approver, re-auth), revoke, per-payment ceiling; applied by the system path only to clean batches (S09). Cut #9 if late.
6. **Gateway top-up and Kleeno Verify.** `src/server/circle/gateway.ts` (own approver wallet only, cap, re-auth, step idempotency, S67); `/api/x402/verify` with the 402 flow and Gateway facilitator settlement (S68). Cut #2 and #3.
7. **UI last** (no Ponytail; `DESIGN.md`, `docs/pages.md`): full `/runs/[runId]` (approve, trace, variance), `/settlement` (plan, signals, holds, signing, standing authorization, status, live-payments request and switch, top-up), admin approvals queue, public receipt page (`/receipt/[token]`, signed, expiring, noindex; cut #7).

Backend slices use Ponytail `full`, then `ponytail-review`. Before any Circle or Arc code I read `../Arc Comtext/AGENTS.md` and the matching `circlefin-skills` file (rule 40), and check current SDK signatures.

## Decisions (defaults; change any before I start)
1. **Who pays when:** the batch runs inline in the plan-signing request (6 workers fits one request), and the recover route finishes anything left `PAYING`. No queue or cron. A "Resume" button covers a closed tab.
2. **Provisioning** runs inline in the admin's approval request, with each step stored, so a retry resumes. A "Resume provisioning" button covers a timeout.
3. **Fallback plan only** in P4. P4b adds the planner on top; holds here are manual (payment approver) or from fired signals shown beside the plan.
4. **Signals never block alone:** a fired signal forces a human signature (no standing authorization); it does not hold an obligation by itself.
5. **x402 buyer side:** the demo buyer must not use a raw private key in Kleeno code (rule 31). I first try Circle wallet typed-data signing; if the SDK can't, the demo buyer is a script that uses a throwaway testnet key from `.env` and holds no value. Seller address is a receive-only platform wallet.
6. **Receipt token:** HMAC-signed, 30-day expiry, one obligation, no payroll detail beyond net amount, tx hash and status.
7. **Rate limits** (S36): per-IP and per-user, DB-backed counters (same pattern as the waitlist), on re-auth, recover, receipt, webhook and verify.

## Done when
1. `npm run lint`, `typecheck`, `test`, `test:invariants`, `test:db` and `forge test` → exit 0; CI green.
2. Gate matrix: one failing check per case → DO NOT PAY + `PAYMENT_EXCEPTION`, `submit` never called. SIMULATION and kill-switch-off runs are rejected everywhere (S05, S06, S08).
3. Four-eyes holds with several roles on one person: the payroll approver cannot sign the plan or be the standing authorization's creator (DB trigger tests, S09).
4. Re-auth: a wrong password gets 401, changes nothing and is audited (a missing password fails body validation with 400 before any check) for approval, signing, hold release, standing authorization, ceiling change and recipient confirmation (S16).
5. Failure and crash matrices pass with fake ports: exactly one on-chain payment, one SETTLED obligation and the right run state for each crash point (S28, S29); the webhook cannot move state (S27).
6. Live demo path on Arc testnet from the UI as two different users: approve payroll → sign plan → every obligation SETTLED from an independent receipt match → run RECONCILED; the arcscan link opens; repeating the action pays nothing twice; on-chain data holds only net amount, recipient and hashed keys.
7. Activation path in the browser: Owner requests → admin approves → wallets and guard appear → Owner switches ON with password + TOTP → OFF stops every path. A demo or sandbox company can't request (DB test).
8. If built: Gateway top-up moves test USDC into the company's own approver wallet only (S67); a paid x402 call returns the allow-listed answer and an unpaid or wrong-amount call returns 402 (S68).
9. The user sees it in the browser. Second-agent review (P4 is a review phase) done and findings fixed or listed.
10. Security rows below `verified`, or `unverified` with a reason. `PROGRESS.md` and `FILE-STRUCTURE.md` updated; one commit; PR; CI green; squash-merge.
