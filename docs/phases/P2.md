# P2 — Foundation (Oct 2–3)

Status: started 2026-09-30 on the user's instruction ("start P2, build it, then we test"). Branch: `p2-foundation`.

## Goal
The trusted base everything else stands on: entities and state machines, config versioning, the full deterministic engine (SALARIED, HOURLY, RETAINER) with trace and hash, audit, field encryption, login with roles/MFA, tenant isolation proven by tests, a workers page. No AI, no CSV (P3), no plan/payment UI (P4).

## Decisions (change any of these before P3)
1. **Overtime weeks:** ISO weeks (Mon–Sun). Overtime is judged per ISO week using only the days inside the pay period; a partial week's threshold is scaled by its weekdays (Mon–Fri) ÷ 5. Reconciliation (P3) buckets hours this way; the engine receives period totals already split into regular / approved overtime / excluded.
2. **Rates and multipliers** use exact bigint fractions (no float, no rounding until the line is rounded half-up to 0.01). Chosen over a decimal library: repeating rates (base ÷ hours) stay exact.
3. **Compensation** lives in a versioned, immutable `compensations` table (new row = new version); values are encrypted (S41). `workers.base_amount` is dropped.
4. **P1 synthetic dev run** (5 USDC, already settled on Arc; tx in `PROGRESS.md`) is cleared from `kleeno-dev` by the migration, because P1 stored its amounts in plain columns that S41 forbids. Re-seedable with `seed-run.ts`.
5. **Encryption key format:** `DATA_ENCRYPTION_KEY=<base64 32 bytes>` is version 1; `vN:<base64>` sets version N, `DATA_ENCRYPTION_KEY_PREVIOUS` holds the old one during rotation.
6. **AI model (P3):** default `z-ai/glm-5.3-flash` on OpenRouter, held in config (`OPENROUTER_MODEL`, `OPENROUTER_FALLBACK_MODEL`), so it can change without code. Confirmed listed on OpenRouter; structured-output behaviour is judged by the P3 model eval.
7. **Login throttling:** failures of known users are audited per company and counted from `audit_events`; unknown emails rely on Supabase's own auth rate limits plus a per-instance throttle.
8. **Recipient-change confirmation** (needs re-auth) moves to P4 with the rest of re-auth (S16); P2 shows the wallet and address only.
9. **Worker lifecycle (added 2026-10-01 at the user's request; Done-when 5 said "edits a worker"):** a promotion, raise, role change or correction is a new immutable compensation version with a reason (applies to the next calculation, never an approved run); pay type can change with it. Leaving archives the worker (`active=false`, `left_on`, `left_reason`); workers are never deleted because runs, obligations and audit reference them, so the code stays reserved. Unpaid obligations of a leaver stay payable (final pay). Archived workers cannot have pay changed until reactivated. New runs must read `listWorkers(..., { activeOnly: true })` (P3 import uses it). Worker code is not editable (it is the key to names held in the browser). Wallets cannot be deleted (Circle custody); changing the payout address waits for P4 re-auth (decision 8).
10. **AI worker setup** (chatbot/assistant proposing new workers) is P3 (AI proposes, human approves); no chat UI exists yet.
11. **Static workers table (accepted for P2):** the user wants dynamic table views (columns, filters, saved views, AI-proposed views) from P3; spec in `docs/pages.md` §5.
