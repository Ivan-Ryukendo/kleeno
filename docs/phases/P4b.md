# P4b — Validated payment planner and standing authorization

Implementation slice under the owner's retained-all-P4 parallel mission, 2026-10-05. Architecture §14.7–14.8 and Essentials rules 18–28 remain authoritative. This spec adds no new payment rail, unrestricted AI tools, live-payment authority or migration application.

## Contract

- Strict PAYMENT_PLAN input: random obligation IDs, pseudonymous worker codes, integer micro-USDC strings, deterministic fired signal IDs/codes, treasury balance and batch total. No names, addresses, notes or raw imports. Output only orders IDs, proposes holds using supported signal reason codes or TREASURY_SHORT, flags existing fired signals and supplies bounded plain-text rationale. Every unpaid eligible obligation appears exactly once; unknown/duplicate/missing IDs and invented amounts/recipients fail validation. Hold citations must belong to that obligation or the run; treasury holds require an actual shortfall. Existing validated/repair pipeline and immutable AIExecution/audit are reused.
- Code hydrates unchanged amounts/recipients from authoritative obligations. Final plan source is the accepted AIExecution ID, or FALLBACK after provider/validation failure. Manual holds always win; existing held obligations cannot be automatically released. AI holds remain proposals until the human signs. Final ordered plan and exact plan hash are stored immutably before authorization.
- Repository callers retain explicit deterministic fallback by default, preserving tests and scripts. The authenticated plan route opts into the planner. Planner setup, treasury-read, and provider failures all retain a deterministic human-signed fallback; invalid manual holds still fail as input errors. Fallback always requires a human signature; no synthetic non-fallback source or invented history enables standing authorization.
- Standing authorization create uses payment role, same-request password re-auth, live-payments check, exact positive monetary limits (payment ≤ batch and company ceiling), future expiry, session company/creator and audit. Revoke reduces authority and needs no re-auth. GET exposes only authorized company records. Routes accept no company/creator/role fields.
- The 1e15 micro-USDC exact-integer ceiling is enforced by code and additive migration `20261005000004_p4b_standing_limits.sql`; the applied P4 migration history remains unchanged. The additive migration fails explicitly if existing grants exceed the ceiling.
- A system path may exercise only a tenant-owned live standing record with a current payment-role creator different from the payroll approver. Require a non-fallback accepted execution, exact unchanged plan/hash, no plan or pre-existing holds, no fresh fired signals, known matching previous-company settled-run config, confirmed current recipients, inclusive limits/ceiling and expiry. Missing evidence requires a human. Atomically claim authorization metadata before the existing compare-and-set state transition; DB trigger repeats four-eyes/roles/standing limits/expiry and kill switch. Existing OwnerPort opens the exact persisted obligation set; no SDK path is added.
- Revocation/expiry/current creator-role removal prevent later standing execution through the existing single gate. Human-signed plans retain their existing behavior. Payroll approval remains human; standing never creates obligations, changes calculations or bypasses gate/guard/settlement.

Targeted unit/invariant checks cover strict privacy/output boundary, missing/extra/duplicate/altered obligations, unsupported citations/hold reasons/rationale, provider failure and invalid output fallback, exact hash/order, manual holds and no automatic release. DB tests cover stored plan/AIExecution/source, creation/revocation routes and auth/reauth, system authorization metadata and state/audit, current checks and concurrency. Fake owner/AI ports cannot make a live payment.
