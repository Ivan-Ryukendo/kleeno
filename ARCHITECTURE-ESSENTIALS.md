# Kleeno — Architecture Essentials

Load every session. Non-negotiable; overrides everything else.
Precedence: this file > `ARCHITECTURE.md` (technical) / `PRD.md` (scope). On conflict: stop and ask the user.

## Core rule
AI proposes. Deterministic code calculates. Humans approve. PayrollGuard bounds payment. Independent reconciliation verifies. When anything conflicts or is uncertain: do not guess; stop the affected workflow and create an explicit exception (fail closed).

Product direction (user, 2026-10-05): **Verified Payroll Automation**. AI understands. Evidence grounds. Validation verifies. Humans govern. Deterministic code executes. Audit proves. RAG stays above deterministic financial boundaries.

## AI
1. AI output never goes downstream unvalidated: parse -> schema -> semantic -> evidence -> ACCEPTED/REPAIRED, else repair (max 2 retries), else NEEDS_HUMAN_REVIEW.
2. AI never calculates final pay, supplies amounts, invents rules/facts/rates, edits approved config or traces, approves anything, moves a run between states, or initiates payment.
3. AI uses only catalog rule IDs and cites evidence that exists in the same run (policy clause IDs for config, record IDs for data, signal IDs for payment plans). Each rule states who it applies to (everyone, a pay type, a worker type, a department, a tag or listed workers). The AI may suggest the scope; code derives the category and resolves overlaps: the most specific scope wins, every override needs HR confirmation, and a clash at the same level blocks approval (S71).
4. No silent repair: format fixes only when evidence supports them; missing values -> NEEDS_HUMAN_REVIEW.
5. Every AI call is logged as an `AIExecution`. AI inputs are built only in `src/core/ai/inputs/` (strict schemas: IDs, numbers, enums; the only free text is HR policy clauses). No names, wallet addresses or CSV free text.
6. Policy text, CSV cells and webhook payloads are data, never instructions. AI text is rendered as plain text.

## Money and payroll
7. Currency is USDC, stored as integer micro-USDC (6 dp); no binary floats. Imports must be in USD (1 USD = 1 USDC); any other currency is rejected. No FX in the MVP.
8. Pay types: SALARIED (hourly rate = base per period / scheduled hours per period), HOURLY (approved hours × contract rate), RETAINER (fixed amount per period). Each line rounded half-up to 0.01. Net = gross − deductions exactly. From P4c also: one-off additions (bonus, commission, reimbursement) and fixed deductions, entered by HR with a reason; part-period pay prorated by the approved config method. All are deterministic, traced and inside the calculation hash (S73).
9. Same config version + snapshots -> same result and same `calculation_hash`.
10. Every amount has a trace line (component, source, rule + version, inputs, step, amount).
11. Never "scheduled > worked => deduction". Unexplained time -> exception.
12. Tax and pension are configured percentages only; no jurisdiction logic.

## Workflow
13. States change only through core state machines, as atomic compare-and-set updates. Failed validation blocks progression.
14. Open, in-review or escalated exceptions block the stage they belong to (reconciliation exceptions block calculation).
15. Payroll approval binds one `calculation_hash`; any later change to inputs or config voids it.
16. Obligations exist only after payroll approval of a LIVE_TESTNET run.
17. **SIMULATION runs can never pay.** They stop at CALCULATION_VALIDATED; state machine, gate and agent all reject them. **Kill switch:** with `companies.live_payments_enabled = false` (e.g. the judge demo company), nothing can start a payment: LIVE_TESTNET run creation, plan signing, standing authorization, `openRun` and every submission are all blocked, in the server and by a DB trigger. A payment approver or the Owner can switch it OFF in the UI (no re-auth). Switching ON needs, once per company, platform-admin approval and provisioning; then only the Owner switches it ON, with password re-auth and TOTP in the same request (S66). `scripts/live-payments.ts` also works. Demo and sandbox companies can never switch ON. All changes are audited. (User decision 2026-10-02; before that, ON was script-only.)
18. The payment authorizer must be a different user from the payroll approver for the same run. Enforced by a DB trigger, including a standing authorization at the time it is used. A member may hold several roles but never approves payroll and authorizes payment for the same run.

## Payment
19. Payment amount == obligation amount == on-chain amount. The payment layer never recalculates; no scaling.
20. The safety gate runs before every submission; any failed check means DO NOT PAY -> PAYMENT_EXCEPTION. There is one gate. `PaymentRail.submit` accepts only a pass the gate issues, and only the payment agent calls it. Webhook, recovery and script paths never pay around the gate.
21. The payment agent acts only on an obligation ID; amount and recipient always come from the obligation.
22. Obligations are paid in authorized payment batches. Each batch is one `PayrollGuard` run: `openRun` (approver wallet) commits the batch's exact obligation set (key -> recipient, amount); `pay(obligationKey)` (agent wallet) pays only a committed, unpaid obligation. Owner calls (`openRun`, `closeRun`, `replaceOperator`) exist only in `src/server/circle/guard-owner.ts`; the agent and rail can only call `pay`.
23. The Payment Planner only proposes order, batch vs `ON_HOLD`, and flags. Its plan holds every obligation exactly once, with no new IDs and no changed amounts or recipients. Authorization signs the final `plan_hash`; execution pays exactly that plan. If the planner fails, a deterministic fallback plan is used; it never blocks a run.
24. `ON_HOLD` is released only by the payment approver into a new signed batch; never automatically.
25. A standing authorization may authorize a batch only if the batch has no holds, no fired signals, no recipient change, the same config version and a non-fallback plan, and is within its limits and expiry. Otherwise a human signs.
26. Never retry blindly: save the attempt (idempotency key) before calling Circle; on timeout, crash or UNKNOWN, check `isPaid` on Arc and Circle first; resubmit only on proven terminal failure.
27. SETTLED only after the Arc receipt independently matches obligation, recipient, amount, token and chain.
28. Payments go through the `PaymentRail` interface; `ArcUsdcRail` is the only implementation. Circle Gateway and x402 are never rails and never pay workers: Gateway only tops up the company's own approver wallet on Arc (S67); x402 only sells the read-only Kleeno Verify answer (S68).

## Chain and security
29. Arc testnet only (chain ID 5042002). USDC ERC-20 = 6 decimals; native gas = 18; never mix.
30. On-chain data is only net amount, recipient address and hashed random run/obligation keys. Never names, worker IDs, gross, deductions or traces. Never publish a name↔address mapping.
31. Secrets live only in git-ignored env files and Vercel env: never in code, the frontend (`NEXT_PUBLIC_`), logs, commits or chat. `src/server` imports `server-only`. Never log raw SDK errors. No private-key CLI flags. Never register the Circle entity secret for the user. Only a Circle `TEST_API_KEY` is accepted. Secrets go only in Vercel's Production scope, never Preview. Inventory: `docs/security.md` §2.
32. Every table has `company_id` and RLS enabled. Supabase's API is public, so logged-in users (`authenticated`) get SELECT only, limited to companies they are a member of (S61); `anon` gets nothing. Every write goes through a server handler or system path and the repositories in `src/server/db/`, which set `company_id` from the session (or from the job's entity) and never from the request. Composite foreign keys `(company_id, id)` make cross-company references impossible. Exception: platform data that belongs to no company (the waitlist and lead list) lives in the `growth` schema, which only the server can reach (`anon` and `authenticated` have no access at all; `docs/phases/W.md`, S51).
33. Handlers never trust company, role, amount or recipient from the request; they derive them from the session and DB. Roles come only from `memberships` (per company; a member may hold several). The active company comes from the session and is re-checked against `memberships` on every request (S61). Mutations live only in `src/app/api` route handlers that authenticate themselves; there are no Server Actions (`"use server"`). `src/proxy.ts` is only a convenience redirect and never the authorization check.
34. Audit events are append-only (DB trigger, binds every role) and cover every high-impact transition.
35. Real business data is anonymised in the browser before upload; names never reach the server. The name key file is passphrase-encrypted in the browser and never uploaded. Names may appear on screen only after the user unlocks the key file in their own browser; they stay in browser memory and are never sent or stored unencrypted.

## Build
36. One phase at a time (P0–P5; P4b can be cut). Exception (user, 2026-10-02): P4 runs in parallel with P3b, P4c and P4d on separate branches, starting after P3b's foundation slice is merged. A phase is done only when its "Done when" checks pass and the user has seen it work. Stay inside PRD scope; out-of-scope ideas go to the user for `docs/roadmap.md`.
37. Stuck rule: after 3 failed fixes on the same problem, stop and write what you tried, the exact error and 2 options into `PROGRESS.md`, then ask the user.
38. Read `PROGRESS.md` first and update it at the end of every session.
39. Protected tests (`tests/invariants/`, `tests/fixtures/`, `contracts/test/`): add freely; never weaken, skip or delete without user approval.
40. Before any Circle or Arc code, read `../Arc Comtext/AGENTS.md` and the relevant `../Arc Comtext/docs/circlefin-skills/` file; check current official docs for SDK signatures.
41. No publicly reachable payment route before P2 auth; P1 payments run from scripts or localhost only.
42. Synthetic data is for development only; never present it as traction.
43. Adding or renaming a folder -> update `FILE-STRUCTURE.md` in the same commit.
44. Ponytail (lean-code plugin) is for backend only: `src/core`, `src/server`, `src/app/api`, `src/proxy.ts`, `supabase/`, `contracts/`, `scripts/`. Use level `full`, never `ultra`. Never use it on `src/app` pages or `src/components` (UI uses shadcn/ui). It never removes ports or `PaymentRail` (single implementation by design), FILE-STRUCTURE folders, protected tests, stack dependencies, validation, audit, idempotency, state machines, security controls in `docs/security.md`, or anything PRD/ARCHITECTURE requires. `ponytail-review` findings are advisory.
45. **UI follows `DESIGN.md`**: §1-9 (warm-cream, pill/stadium, ink-black style) for the public pages (landing, `/privacy`, 404, admin); §11 "Product UI" (white, hairlines, 6-8px radii) for every signed-in page and the auth pages, scoped by the `app-theme` class and the page map and intended feel in `docs/pages.md`. Read it before touching `src/app` pages, `src/components`, `src/app/globals.css`, `layout.tsx` or any styling. Tokens (colours, fonts, radii, shadows) live once in `globals.css` and the shadcn theme; components use tokens, never hard-coded hex. Kleeno adaptations, which override `DESIGN.md` on conflict:
    - No Mastercard logo, red or yellow, and no MarkForMC; use Sofia Sans (`next/font`, body weight 450, headlines 500 at -2% tracking).
    - Signal Orange (`#CF4500`) is only for approval, exception, DO NOT PAY and other compliance signals, never marketing CTAs.
    - Orbit arcs, circular portraits and ghost watermarks are for the landing page and empty states. Working screens (tables, forms, approvals, traces) use the same tokens with dense, readable layouts, never decorative motifs.
    - Radii on the public pages are 20px (buttons), 40px (large containers) or full pill; dense tables and inputs use 20px or pill, not 8–16px. Signed-in pages use the product radii of `DESIGN.md` §11 (card 8px, field 6px, chip 4px) through tokens, with no pills.
    - Text must stay readable: no Dust Taupe for essential text; keep WCAG AA contrast. Success or error colours `DESIGN.md` lacks are proposed to the user before use.
    - Motion is short (150–250 ms) and functional: a state change, progress, reveal or hover lift. It never delays an approval or hides an amount, and it honours `prefers-reduced-motion` (`DESIGN.md` §10).
    - AI text and untrusted data stay plain text (rule 6); the design never changes any other rule.

## Security layer
46. Security controls are listed in `docs/security.md` (IDs S01–S82, each with its phase and test; S76–S82 planned for conditional P4r). Every `Pn.md` copies that phase's rows into "Done when". A phase is not done until its rows are `verified`, or `unverified` with a stated reason. Never assume a control works.
47. Re-authentication: the server checks the user's password in the same request for anything that grants or widens payment authority (payroll approval, plan signing, hold release, standing-authorization create, per-payment ceiling change, recipient confirmation). Actions that only reduce authority (revoke, place hold, live payments OFF) never require it.
48. Approved records are immutable in the database (triggers bind the service role too): calculations, lines, snapshots, approvals, approved config versions, AI executions and audit events. For obligations, only status, batch, tx hash and timestamps may change. Any other change needs a new run.
49. Every idempotent operation is backed by a DB unique constraint, not only by application code (imports, wallets, obligations, payments, attempts, webhook notifications, guard runs).
50. Uploaded business data is confidential. It moves only over HTTPS. Every field that reveals pay levels or policy is encrypted per company (AES-256-GCM, envelope key) in the `src/server/db` repositories before it reaches the database (`docs/security.md` S41). Payroll values never appear in logs, errors or audit payloads. Users of real companies sign in with MFA.

## Integrations
51. External systems (HR, payroll, time, accounting, expense, document, notification, identity) and MCP clients are evidence sources or destinations, never authorities. Their data enters only as normalized evidence through the same mapping, USD check, validation, reconciliation and snapshot path as a CSV import. Their approvals are evidence, not Kleeno approvals; their computed pay is only "actually paid" evidence for variance. They never change rules, amounts, recipients, states or approvals, create obligations, or authorize or execute payments. Their webhooks are hints: verify, dedupe, re-fetch.
52. Code asks for capabilities, never vendors. Providers are typed descriptors in `src/core/integrations/`; vendor code lives only in `src/server/integrations/<provider>/`; `src/core` never names a vendor. An undeclared capability fails closed. No capability for approval, payment, recipient or state change exists.
53. Every imported record carries provenance (source provider, connection, object type, object ID, version, fetched at, hash, reference); raw external payloads are not stored. Run snapshots reference evidence IDs and source hashes. A later change at the source creates a new evidence version and never alters an approved snapshot or calculation.
54. Integration credentials are server-only, least-privilege and never in logs, prompts, audit payloads or plain records: per-company tokens are encrypted with the company data key (S41), platform OAuth app secrets live in env. No second secret store; disconnect revokes and deletes tokens. Kleeno's AI agents never get connector or MCP tools; external data reaches AI only through `src/core/ai/inputs/`. Notifications carry no payroll data (counts, state and a link only).
55. The Kleeno MCP server (after the hackathon) is read-only: no tool writes, approves, resolves, creates obligations, changes recipients or config, authorizes or pays. It uses the same auth guard, `memberships` roles, MFA, company and object checks, rate limits and audit as route handlers; tool annotations are hints, never security. External identity providers only authenticate; `memberships` alone grants roles. Design: `docs/integrations/`.

## Git and publishing
56. Git and GitHub follow `docs/github.md`. Commit with the GitHub noreply email only. Before every commit, run a staged secret scan and the checks, and never stage env files, keys, recovery files or real data. Work on one branch per phase and merge to `main` only by squash-merging a PR with green CI. Never force-push, rewrite history, skip hooks or disable a check. The repo stays private until the P5 going-public checklist passes and the user approves the visibility change.

## Evidence-Grounded AI and Controlled Learning (user, 2026-10-05)
57. Retrieval grants no authority. Every consequential recommendation must identify valid approved evidence or become NEEDS_HUMAN_REVIEW. Citation existence alone does not prove support: verify supported structured claims against exact records and pinned approved configuration; ambiguous prose/conflicts escalate. Policy citations bind source/version/clause; record citations bind the correct company/run/worker. AI cites only evidence supplied in its validated input package.
58. Tenant, permitted source/config version, approval, effective period and embedding generation restrictions belong inside each database candidate query before ranking/LIMIT, never an unrestricted vector query followed by company filtering. Exact known rule/clause IDs take precedence; semantic scores never override scope, version or authorization. Re-check stale/revoked evidence at acceptance. Ranking scores are not business confidence.
59. Core depends on retrieval/embedding interfaces, never a provider/framework SDK. Prefer existing Supabase pgvector and native adapters; LangChain is optional and has no role in authoritative payroll, validation, approval or payment behavior. Retrieval failure never bypasses existing validation or changes approved hashes, amounts, recipients or obligations.
60. Embed approved, sanitized company knowledge only, through strict input construction; no names, bank/wallet data, raw payroll CSVs, unrestricted compensation or arbitrary employee/resolution notes. MVP AI prompt free text remains approved policy clauses under rule 5; precedent uses typed facts/enums. Future approved knowledge summaries need an explicitly reviewed input-schema extension, never raw notes. Preserve rule 50 encryption; searchable vectors/lexical indexes require an explicit data-classification/storage decision before implementation. Real business data requires review of the actual provider's current data-use/retention terms; credentials stay server-side. Begin with synthetic fixtures.
61. Knowledge memory (approved documents), resolution memory (finalized human-approved precedent) and operational history (authoritative immutable facts) are separate. Learning creates proposals, not authority: no automatic config mutation or model-weight updates; proposed rules need human approval as a new immutable version. Rejected AI suggestions and unfinalized outcomes are not trusted precedent.
62. Extend AIExecution and append-only audit for retrieval IDs/hashes, corpus/model/config versions, cited subset, validations, human decisions and resulting actions; never build a competing log or expose private chain-of-thought. Audit payloads exclude sensitive raw queries/content. Preserve deletion guarantees and test new artifacts; vectors/backups do not gain crypto-shredding merely because source text is encrypted.
63. Conditional retrieval phase P4r follows stable source/config boundaries and the core payroll/payment checkpoint; tests/fixtures precede code, with zero tenant-isolation failures, disallowed-version overrides and unsupported accepted claims. The October 17 extension primarily funds validation/demo/testing/polish; schedule and freeze are in PRD §12. If retrieval cannot safely fit, defer it, preserving the existing demo and all protected tests/financial controls.

## Future architecture decisions (2026-10-06; planned, not active)

The owner approved documenting a future product roadmap, not changing runtime behavior. [Ordered steps and gates](docs/roadmap.md#future-product-delivery-sequence-approved-direction-2026-10-06) distinguish current hackathon scope, a commercial review workspace, and a later full United States payroll service. Rules 1-63 above remain active; none is relaxed by this section.

- **Policy priority (Step 5):** baseline plus explicit per-rule overrides with applicability separate from priority. Existing scope/specificity behavior remains until a versioned extension preserves old configurations. HR may rank a group above personal only through impact preview, reason and approval; equal-priority clashes block. Upload order and embeddings never decide precedence.
- **Commercial review (Step 6):** future sign-off binds immutable review evidence and has a separately specified lifecycle. It must not reuse payroll/payment authorization or create obligations. SIMULATION still stops at CALCULATION_VALIDATED and can never pay.
- **Platform operations (Step 7):** extend existing admin authorization with narrowly scoped support/billing/operations capabilities. Registered users are not waitlist contacts or workers. Support initially sees metadata and deliberately submitted evidence, not arbitrary payroll data; no unrestricted impersonation, approval, recipient mutation or payment authority.
- **Employee identity (Step 8):** approved future direction is a company opt-in exception for encrypted names/basic contact details, default off. Rule 35/S25 remains unchanged until the access/encryption/deletion design and tests pass and the active rules are amended together. Exclude these fields from AI, chain, logs and audit payloads. Real-data employee access requires MFA and self-only authorization. Broader files/medical records are outside the initial exception.
- **Billing (Step 9):** subscription collection is distinct from payroll disbursement; trial expiry/payment of a subscription grants no financial authority. Start in Stripe test mode; business registration and provider activation gate live collection. Demo workspaces cannot pay.
- **Connectivity and AI (Step 10):** retain rules 51-63. Read-only API/MCP uses existing access controls. Real embeddings require a reviewed searchable-data/privacy design; existing synthetic results do not authorize real sensitive-data ingestion.
- **Reliability and production (Steps 11-12):** measure availability/recovery objectives and demonstrate restoration before commercial launch. Arc remains testnet; production rails/jurisdictions need a separately approved specification and security/legal/provider gates. No automatic retry or provider failover may bypass settlement reconciliation.
- **UI (Steps 3-4):** future navigation/graph/table direction lives in DESIGN and the page map; current routes/styles are not changed by documentation. Backend records remain authoritative across all views.

Activation requires a bounded phase specification, applicable owner decisions, version/migration compatibility, security tests and evidence, and synchronized updates to active architecture/PRD/security rules. Reuse existing services and database relationships; no mandatory graph database, new workflow engine or competing audit log.
